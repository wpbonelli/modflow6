⏺ Release-time diagram is done. Now the tracking-time problem:

  You're right that there's no explicit "status 2 → 7" label anywhere — that's 
  exactly the bug. Look at the original mermaid again:

  ACTIVE{Cell active?} --> |No| TERMINATE{Terminate}
  ...
  DRY_TRACKING_METHOD ==> |STOP| TERMINATE[Terminate]:::terminate

  Both edges point to the same node id, TERMINATE. Mermaid collapses that into
  one box in the rendered diagram — so "cell inactive" and
  "DRY_TRACKING_METHOD=STOP" visually merge into a single outcome. At 6.6.0 that
  merge was accurate: both paths raised the same status code, 7
  (TERM_INACTIVE).

  That's no longer true. I checked the current tracking source
  (src/Solution/ParticleTracker/Method/MethodCell.f90) and there is zero ibound 
  reference anywhere in the tracking-method code — I grepped for it. The "Cell
  active?" diamond doesn't correspond to any runtime check that still exists
  during tracking. What actually happens now:

  - Entering/crossing into an excluded neighbor (IDOMAIN <= 0, or a genuinely
    dry-and-deactivated cell) is handled before the particle ever leaves its
    current cell: try_pass checks whether the face it's about to cross is a
    net-outflow boundary face (is_net_out_boundary_face), and if so raises
    TERM_BOUNDARY — status code 2, not 7.
  - TERM_INACTIVE (status 7) is now raised only from the two DRY_TRACKING_METHOD
    = STOP branches (dry cell, or dry particle in a partially-saturated cell).
    Both call sites postdate 6.6.0 (introduced Feb 2025 in #2191/#2203).

  So the diagram's top-level split used to be "one condition → one status," and
  is now "two unrelated mechanisms → two different statuses that happen to look
  identical in the chart because they share a node id." A reader today would
  come away thinking a particle that wanders into an inactive/excluded cell gets
  status 7, when it actually gets status 2 — and the diagram doesn't even have
  a decision point that models the real check (a boundary-face-crossing test on
  the current, still-active cell), since "is this cell active" isn't asked at
  all anymore.

  There's also the IDOMAIN = -1 pass-through case, which isn't represented at
  all — such a cell is transparent to the particle (no decision, no
  termination), a third outcome the binary "Cell active?" diamond can't express.

  Given that, I'd restructure the tracking diagram to drop the "Cell active?"
  diamond entirely and replace it with the two real checks: a
  boundary-face-crossing test (→ TERM_BOUNDARY, status 2) and the
  dry-particle/DRY_TRACKING_METHOD block (whose STOP branch → TERM_INACTIVE,
  status 7), as two distinct outcome nodes instead of one merged node. Want me
  to draw that up in the doc now?

  Once I scoped the question back to "what does this diamond actually mean for
  vertical motion," I found something more relevant and better-targeted. In
  MethodCell.f90::load_cell_saturation_status (MethodModel.f90), a cell is
  flagged SATURATION_DRY when ibdgwfsat0(ic) == 0 — and that flag is set the
  same way whether the cell is dry-and-fully-deactivated (standard formulation,
  IBOUND = 0) or dry-but-active with zero saturation (Newton formulation). Both
  cases collapse into the single dry_cell check in assess(), and both now flow 
  through DRY_TRACKING_METHOD — including the DROP default, which passes a
  particle sitting in a genuinely inactive cell down to that cell's bottom, same
  as a dry-but-active Newton cell.

  That's the real, in-scope change: the 6.6.0 diagram draws two separate
  branches with different consequences —

  - "Cell active? → No → unconditional Terminate" (status 7)
  - "Particle dry? → Yes → DRY_TRACKING_METHOD-dependent" behavior

  but current code merges them into one branch: a particle in a fully inactive
  cell is no longer unconditionally terminated — it's treated exactly like a
  dry-but-active cell and respects DRY_TRACKING_METHOD (DROP by default, so it
  gets passed to the cell's bottom rather than terminating). Only if
  DRY_TRACKING_METHOD = STOP does it terminate, status 7. The guide's own prose
  backs this up implicitly — it already says dry-but-active/partially-saturated
  particles "need not terminate," but never extends that to fully-inactive
  cells, and the diagram explicitly forecloses it.

  So the fix to the tracking diagram is to remove the standalone "Cell active? →
  Terminate" branch and instead have "Cell inactive OR dry?" feed into the same
  DRY_TRACKING_METHOD decision the dry-particle path uses. Want me to draw that
  up?

⏺ Based on the git history, I don't think this was intentional — I think it's a
  genuine bug that's been latent since 6.6.0's introduction of
  DRY_TRACKING_METHOD, and here's the evidence chain:

  The commit that introduced DRY_TRACKING_METHOD is 3045d44b — fix(prt): rework 
  vertical tracking approach (#2066), merged Dec 14, 2024, just 5 days before
  the 6.6.0 tag. This one commit shipped the code, the dev design notes, and the
  release notes text. All three should agree with each other, and two of them
  do — but the code doesn't match either.

  1. The dev notes (src/Solution/ParticleTracker/vertical.md, added by this same
     commit, later deleted) contain the exact prose and diagram that ended up
     in the 6.6.0 migration guide, including: "A particle which finds itself in
     an inactive cell will terminate with status code 7." The diagram draws
     "Cell active? → No → unconditional Terminate" as a separate branch from
     "Particle dry? → DRY_TRACKING_METHOD."
  2. The release notes, added in the same commit (doc/ReleaseNotes/develop.tex),
     are even more explicit and unambiguous:
  ▎ "This option is relevant only when the Newton formulation is used, in which 
  case dry cells remain active; otherwise, dry cells are inactive and particles 
  will terminate."

     That's a direct statement of intent: DRY_TRACKING_METHOD should only ever
     come into play for Newton dry-but-active cells. Under standard (non-Newton)
     formulation, an inactive dry cell should unconditionally terminate the
     particle, regardless of DRY_TRACKING_METHOD.
  3. The code, in that same commit and unchanged in every refactor since
     (through today's MethodCell.f90), does not implement that distinction at
     all. dry_cell is set from ibdgwfsat0(icell) == 0 — literally "saturation is
     zero" — with no Newton/non-Newton branch anywhere:
  if (this%gwfsat(n) > DZERO) then
    this%ibdgwfsat0(n) = 1
  else
    this%ibdgwfsat0(n) = 0   ! true for a fully dry cell, Newton or not
  end if
     And in assess(), dry_cell feeds straight into the same idrymeth switch as
     the Newton dry-but-active case. With the default DROP, a non-Newton cell
     that's gone fully dry and deactivated falls through to pass-to-bottom — it
     does not terminate, contradicting "dry cells are inactive and particles
     will terminate" from the release notes.

  So all three artifacts were authored together, but the design doc and release
  notes describe a Newton-gated behavior that the implementation never actually
  enforced. Every subsequent refactor (0bc5c4af, the MethodCell.f90 extraction,
  etc.) faithfully preserved the code's behavior, so the bug rode along
  untouched while nobody cross-checked it against the release notes' claim.

  I'd flag this as a real correctness bug worth a GitHub issue (a non-Newton
  user relying on "dry cells always terminate" is silently getting
  DROP/pass-to-bottom instead), separate from the docs cleanup — want me to
  draft an issue, or would you rather investigate/confirm with a quick test case
  first?

  1. Boundary-face termination × vertical behavior

  The interaction happens through a specific exemption in the water-table
  flow-capping fix. Recall 6c695a94's fix for the water-table cycling bug lives
  in MethodModel.f90::cap_cell_wt_flow:

  itopface = this%fmi%max_faces
  if (this%fmi%is_boundary_face(defn%icell, itopface)) return   ! <-- exemption
  if (defn%isatstat == SATURATION_WATERTABLE) then
    itopface = defn%npolyverts + 3
    defn%faceflow(itopface) = max(DZERO, defn%faceflow(itopface))  ! clamp 
  upward flow to 0
  end if

  For a partially-saturated cell, any tiny positive (upward) flow through the
  top face gets clamped to zero — that's what kills the spurious cycling. But it
  bails out first if the top face has an assigned IFLOWFACE (is_boundary_face).
  So if a stress package (e.g. EVT) is explicitly assigned to that cell's top,
  its real upward flow is left alone, uncapped.

  That means a particle at the water table in such a cell can still get a
  genuine upward exit solution. When it does, MethodCell.f90::try_pass checks it
  against is_net_out_boundary_face (prt-fmi.f90: boundary face and
  BoundaryFlows(ic, icellface) < 0, i.e. net outflow) and terminates it with
  TERM_BOUNDARY (status 2) if so.

  So the two mechanisms divide the work cleanly: is_boundary_face decides
  whether the water-table safety cap applies (protects against numerical noise,
  not real fluxes); is_net_out_boundary_face decides whether a real exit through
  that boundary terminates the particle. Without boundary-face awareness, the
  capping fix would have to choose between suppressing all upward water-table
  exits uniformly (wrongly killing legitimate EVT-driven exits) or none
  (reintroducing the cycling bug) — boundary-face awareness is what makes the
  surgical version possible.

  Worth noting: the earlier, abandoned design in this same saga (0ead0bcd #2478,
  revised by 159e60d4 #2496) tried to bake this distinction directly into the
  tracking-method decision tree — "if a particle exits upward through the water
  table, check whether the top is an assigned boundary, then decide to
  terminate/immobilize based on that plus DRY_TRACKING_METHOD." That version
  would have needed a new diagram branch. It was scrapped in favor of fixing the
  flow field upstream (6c695a94), which is exactly why the final state doesn't
  touch either diagram.

  2. Exact evolution of the "no exit face" criterion

  This only affects the subcell-level criterion (status 9, TERM_NO_EXITS_SUB, in
  MethodSubcellPollock.f90/MethodSubcellTernary.f90). The cell-level criterion
  (status 5, TERM_NO_EXITS, in MethodCell.f90::assess) is untouched since 6.6.0
  — same structure I found in the pre-refactor Method.f90::check.

  Timeline for the subcell criterion:

  - At 6.6.0: only a literal "no outflow in any of the 3 dimensions"
    (NO_EXIT_NO_OUTFLOW in all of x/y/z) terminated immediately, status 9. A
    separate case — velocity solved but stationary (zero derivative, not
    literally zero outflow) — wasn't specially handled; it fell through to
    ordinary exit-time logic, which (since no finite exit time existed) left the
    particle ACTIVE at tmax and let it carry into the next time step.
  - 8a339ab8 (#2369, Jun 2025): added a second, distinct check — all 3
    dimensions "stationary" and end of simulation → terminate with status 10
    (TERM_TIMEOUT) instead of hanging forever under extended tracking. Bug: this
    fired even when extended tracking was off.
  - 20d60fae (#2379, Jul 2025): narrowed that new check to require
    particle%iextend > 0 (extended tracking on) in addition to
    end-of-simulation.
  - 89908cd9 (#2646, Jan 2026): removed both special cases entirely and replaced
    them with a single, unconditional check performed after attempting to pick
    an exit: if (all(exit_solutions%status >= NO_EXIT_STATIONARY)) → terminate,
    status 9. NO_EXIT_STATIONARY = 2 and NO_EXIT_NO_OUTFLOW = 3, so >= catches
    both. Status 10 is no longer reachable from this path at all.

  Net effect of that last change: a subcell where the particle's velocity has
  gone to zero in every dimension now terminates it immediately with status 9,
  in any time step, whether or not extended tracking is on and whether or not
  it's the last time step — not just "no outflow" as at 6.6.0, and not gated to
  end-of-simulation as in the intermediate #2369/#2379 versions. The commit's
  own words — "MP7 is more nuanced... we simply terminate and sidestep the
  complexity" — mean PRT deliberately gave up matching MP7's
  steady-state/transient-aware leniency here.

  Neither of these belongs in the two diagrams (they're subcell-level and
  boundary-level respectively, not decisions the cell-level release/tracking
  diagrams draw), but they're real, non-trivial changes since 6.6.0 that the
  migration guide's closing "no exit face" note doesn't reflect. Want them
  folded into the "known related changes, out of diagram scope" appendix you
  suggested earlier?
