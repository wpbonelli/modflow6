PRT Exchange Refactoring Plan
==============================

Date: 2026-03-16
Branch: prt-claude-exg

## Summary

Refactor PRT exchange architecture to:
0. Refactor event system to use procedure pointers instead of consumer type hierarchy
1. Move do_transfer() from BaseExchangeType to PrtPrtExchangeType only
2. Implement connection linking (gwfconn2prtconn, link_connections) for GWF-PRT exchange
3. Replace hardcoded outbox logic with generic event-based mechanism
4. Introduce exchange PRP package (index 0) to handle transferred particles
5. Keep has_pending() on ExplicitModel

## Background

Current issues (from prt_exg_notes.txt):
- do_transfer() shouldn't be on base exchange type (only needed for discrete object transfers)
- Missing connection linking like GWF-GWT/GWF-GWE exchanges
- Particle event mechanism is too specific (explicit consumer class instead of generic)
- Outbox logic is hardcoded in prt_solve() (lines 1122-1125, 1150-1153)

## Architecture Overview

### Event-Based Boundary Handling

When a particle reaches a model boundary:

1. Tracking method dispatches BOUNDARY_REACHED event (where TERM_BOUNDARY is currently dispatched)
2. PRT-PRT exchange (subscribed to both models' event dispatchers) receives event:
   - Checks if particle%icu is in nodem1 or nodem2 (claimed boundary)
   - If CLAIMED: Adds particle to destination model's exchange PRP, dispatches CLAIMED event
   - If NOT CLAIMED: Sets status=TERM_BOUNDARY, dispatches TERMINATE event
3. Source model (subscribed to CLAIMED events) marks particle as transferred/skip
4. Output handler (ParticleTracksType, subscribed to TERMINATE) writes termination record
5. After tracking loop completes, source model skips transferred particles in future iterations

### Exchange PRP Package

- Special PRP package with index 0 (iprp = 0)
- Always exists on PRT models (created during model setup)
- Empty/non-functional unless exchanges are configured
- Receives particles transferred from neighboring models via exchanges
- Processed uniformly in tracking loop alongside regular PRPs

### Connection Linking

Following GWF-GWT/GWF-GWE pattern:
- PRT-PRT exchange has gwfmodelname1, gwfmodelname2 fields
- gwfconn2prtconn() finds matching GWF-GWF ↔ PRT-PRT connection pairs
- link_connections() establishes pointers to flow fields (simvals) for tracking
- Supports flow consolidation for refined/coarse cell mappings

## Implementation Tasks

### Task 0: Refactor Event System to Use Procedure Pointers

Files: src/Solution/ParticleTracker/Particle/Events/ParticleEvents.f90

**Problem:** Current consumer type hierarchy is inflexible. To make exchange and model event consumers, we'd need wrapper types with back-pointers (kludgy). Procedure pointers with context allow objects to register callbacks directly without inheritance constraints.

0.1. Define abstract interface for event callbacks
     - New interface in ParticleEvents.f90:
       ```fortran
       abstract interface
         subroutine event_callback(context, particle, event)
           import :: ParticleType, ParticleEventType
           class(*), pointer :: context  ! pointer to object with state
           type(ParticleType), intent(inout) :: particle
           class(ParticleEventType), intent(in) :: event
         end subroutine
       end interface
       ```

0.2. Create EventSubscription type
     - Replaces storing consumer objects
     - Contains both procedure pointer and context pointer:
       ```fortran
       type :: EventSubscription
         procedure(event_callback), pointer, nopass :: callback
         class(*), pointer :: context
       end type
       ```

0.3. Update ParticleEventDispatcherType
     - Replace `consumers` list with `subscriptions` list
     - Change subscribe() signature:
       ```fortran
       subroutine subscribe(this, callback, context)
         procedure(event_callback) :: callback
         class(*), pointer :: context
       ```
     - Update dispatch() to call: `subscription%callback(subscription%context, particle, event)`

0.4. Remove ParticleEventConsumerType
     - No longer needed
     - Delete abstract base type

0.5. Update ParticleTracksType
     - Remove `extends(ParticleEventConsumerType)`
     - Keep all state (files, selection flags, etc.)
     - Create module procedure `tracks_handle_event(context, particle, event)` in ParticleTracksModule
     - In tracks initialization, register callback:
       ```fortran
       call this%events%subscribe(tracks_handle_event, this%tracks)
       ```

0.6. Update tracks_handle_event callback
     - Module procedure in ParticleTracksModule
     - Signature matches event_callback interface
     - Uses select type to extract ParticleTracksType from context
     - Implements existing handle_event logic

### Task 5: Register PrtPrtExchange as Event Callback

Files: src/Exchange/exg-prtprt.f90

5.1. Create exchange_handle_event callback
     - Module procedure in PrtPrtExchangeModule
     - Signature matches event_callback interface:
       ```fortran
       subroutine exchange_handle_event(context, particle, event)
         class(*), pointer :: context
         type(ParticleType), intent(inout) :: particle
         class(ParticleEventType), intent(in) :: event
         type(PrtPrtExchangeType), pointer :: exchange
       ```

5.2. Implement exchange_handle_event logic
     - Use select type to extract PrtPrtExchangeType from context
     - Handle BOUNDARY_REACHED events
     - Check if particle%icu is in nodem1 (model1 -> model2 transfer):
       * Find all connections for particle%icu in nodem1
       * If multiple connections: call geometric selection to pick destination cell
       * If single connection: use nodem2 directly
       * Add particle to prtmodel2%exchange_prp%particles with selected cell
       * Set particle%iprp = 0 (exchange PRP)
       * Set particle%icu to destination cell
       * Dispatch CLAIMED event to prtmodel1%events (source model)
     - Check if particle%icu is in nodem2 (model2 -> model1 transfer):
       * Same logic, reversed direction
       * Add particle to prtmodel1%exchange_prp%particles
       * Dispatch CLAIMED event to prtmodel2%events (source model)
     - If neither match (not this exchange's boundary):
       * Set particle%istatus = TERM_BOUNDARY
       * Dispatch TERMINATE event to source model's events

     Note: Exchange accesses exchange_prp via model's package list (iprp = 0)

5.3. Subscribe to model event dispatchers during exg_ar
     - Register callback with both models:
       ```fortran
       call this%prtmodel1%events%subscribe(exchange_handle_event, this)
       call this%prtmodel2%events%subscribe(exchange_handle_event, this)
       ```

## Design Decisions and Trade-offs

### Why Procedure Pointers Over Consumer Type Hierarchy?

Pros:
- No inheritance constraints - any object can register callbacks
- Avoids kludgy wrapper types with back-pointers
- Objects maintain all their state naturally
- More flexible - matches original design vision from notes
- Cleaner conceptually

Cons:
- Requires refactoring existing event system
- Callbacks defined as module procedures (not type-bound)
- Context pointer requires select type cast in each callback

Decision: Use procedure pointers. We're already doing significant refactoring, and this avoids accumulating technical debt.

### Why Event-Based Over Bitmask?

Pros:
- More flexible - exchanges can implement custom logic
- Cleaner separation - tracking methods don't need exchange knowledge
- Extensible - easy to add new callbacks later

Cons:
- More complex event flow
- Performance overhead of event dispatch (likely negligible)

### Why Exchange PRP Over Inbox?

Pros:
- Uniform treatment of all particles (regular + transferred)
- Natural fit with PRP package architecture
- Simpler - no special inbox processing loop

Cons:
- Requires special iprp = 0 handling
- Always created even if unused

### Why Keep has_pending on ExplicitModel?

Pros:
- Polymorphic - supports future discrete object models
- Existing ExplicitSolution loop structure
- Model encapsulates its own state

Cons:
- Somewhat PRT-specific despite being on base class

## Open Questions

1. Memory management for transferred particles
   - When particle marked istransferred, when is memory freed?
   - PRP store structure-of-arrays makes removal complex

2. Exchange PRP capacity
   - How to size exchange PRP particle store?
   - Resize dynamically during transfer?

3. Geometric selection implementation
   - Which DisvGeom utilities to use?
   - How to handle DIS vs DISV differences?
   - What about DISU?

4. Exchange PRP particle state
   - What status should particles have in exchange PRP? ACTIVE?
   - Are they immediately ready to track in next iteration?
   - Do they need any special initialization?

5. Multiple exchanges per model
   - We assume at most one PRT-PRT exchange between two models
   - But a model could have exchanges to multiple neighbors on different boundaries
   - Each exchange subscribes to events and checks if boundary is claimed
   - First exchange to match claims the particle (should only be one match)
